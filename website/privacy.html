Privacy policy

Last updated: 2026-10-15. This page covers the official Kodeoff account relay, the website’s no-signup file-sharing channel, and self-hosted relays, across the iOS, macOS, and web clients. The iOS App Store build connects to the official HTTPS service; data of dedicated self-hosted builds is handled by the operator of the chosen server.

The short version

Email, account information, files, and clipboard text are transmitted to the relay server you are currently connected to. The server operator can access the stored data; when using a self-hosted service, make sure the server is run by someone you trust.

The app currently contains no third-party analytics, advertising, or tracking components. Sending between devices is not end-to-end encryption — how the server handles data also affects your privacy.

1. Scope

The official Kodeoff service is operated by the developer, Kai Yu, and connects devices of the same account via https://relay.kodeoff.com. The developer and authorized administrators may access account, device, file, and operational information on the official servers to provide and maintain the service. When using a self-hosted relay, data is handled by the operator of the server you chose; providing the clients does not automatically give the developer access to that server’s data.

The app embeds no third-party SDKs and contains no analytics, advertising, or tracking components. The privacy manifest bundled with the app (PrivacyInfo.xcprivacy) conservatively declares the data categories involved in the account relay (email identifier, device and account identifiers, user file content, diagnostics — none used for tracking); the official service processes and stores this data for account verification, device management, file and text transfer, security, and troubleshooting — not for advertising or cross-app tracking. Self-hosted services are the responsibility of their operators.

2. Where data goes and why

Account login and relay transfer connect to the official service built into the build, or to the self-hosted server chosen in a dedicated build. 3. Anonymous sharing (no-signup web upload)

Channel status (2026-10-20): no-signup web upload is paused; the share page has been replaced by a pause notice. This section remains to document how data was handled for existing links during their natural expiry window (24 hours).

The website’s no-signup share page allowed uploading a single file and generating a download link without registering an account (the terms of service applied). Content handled by this channel: the file itself, its name, size, and SHA-256 checksum — solely to serve downloads to link holders, for no other purpose.

Retention: links were valid for 24 hours from creation and up to 20 downloads; on expiry, exhaustion of downloads or traffic quota, cancellation before completion, or timeout, the file was deleted from the server automatically (server copies included). The anonymous pool has no backups; deleted means unrecoverable.

Not collected: anonymous uploads required no account, email, or password; the official service did not record visitor IPs on this channel. The one-time management credential shown on the upload-complete page existed only in your browser page’s memory — the server stored only its hash and cannot reconstruct it; once the page closed, it was gone.

Report data: links and descriptions submitted via the download page’s “Report abuse” entry or the reporting guide were used solely for verification and takedown, for no other purpose, and are never shared with the reported party.

4. No tracking & store privacy notes

No tracking components does not mean the online service processes no user data. The App Store privacy label must cover what the actually shipped build — plus the developer and partners — can access: the official service’s label declares email, user and device identifiers, file content (including photos, video, audio, and other user content), and operational diagnostics; this data is linked to the account, used for app functionality, and not used for tracking. Definitions per Apple’s App privacy details.

The app uses UserDefaults (reason code CA92.1) for its own preferences, and the disk-space API (reason code E174.1) to check whether a file fits before downloading. When space is short, the download stops and you are asked to free space; disk-capacity information is never sent to the server. Both uses match the privacy manifest.

5. Official service status

The official service is https://relay.kodeoff.com, operated by Kai Yu on Aliyun servers in Tokyo, Japan (ap-northeast-1). Registration is currently invite-only: new accounts need a valid invite code; existing accounts sign in with email and password. Verification and password-recovery emails are sent via Resend from noreply@kodeoff.com.

The mail provider processes recipient addresses, message content (including verification codes), and delivery status; it never receives your password or relay files. Mail-related data may also be processed in other regions such as the United States, per the provider’s policy. See the Resend privacy policy. Contact and feedback channels are in section 10 of this page.

6. On-device storage

Credentials: the device login credential is stored in the iOS system keychain, protected by system encryption; it is deleted promptly on sign-out or revocation.

macOS credentials: kept in ~/Library/Application Support/Kodeoff/credentials.json with directory permissions 0700 and file permissions 0600; the app does not read the keychain. The file itself is not additionally encrypted — programs running as the same system user may read it.

Web credentials: kept in the current browser’s local storage, cleared on sign-out. Avoid staying signed in on untrusted public computers.

Preferences: server address, device ID, account code, download policy, cache retention days and the like live in local preferences (UserDefaults) as the app’s own settings.

Inbox cache: downloaded deliveries and the offline list snapshot live inside the app sandbox, kept for 30 days by default and cleaned automatically after; adjust retention or clear everything under Settings → Local cache.

Photo library: written only when you actively save a received image/video to Photos; the app never reads your photo library.

7. What permissions are for

Local network: used to reach the self-hosted relay you specified (for example a Mac or other host on your LAN). The system prompt appears on first connection; denying it blocks LAN servers only, nothing else.

Photo library (add-only): used to write images/videos you chose to save into Photos. The app never reads your photos.

Beyond these two, the app requests no other privacy permissions.

8. An honest account of transport & storage security

The official service uses HTTPS transport and mail is submitted over encrypted SMTP. There is no end-to-end encryption today: the server can read the files and metadata it stores. The security of a self-hosted service depends on its operator’s setup — configure TLS for cross-network use; plaintext HTTP is only fit for local testing in dedicated development builds.

On an unencrypted link, a man-in-the-middle on the same network can see what is transferred; the server stores files and metadata in plaintext (credentials are stored hashed only). Judge your deployment accordingly. This app makes no security claims beyond these facts.

9. Retention & deletion

Online accounts, devices, and inbox content on the official service are kept until you delete them; account quotas and item limits exist to control storage. No scheduled business-data backups are enabled today; operational logs rotate by space on the server system, with no separate per-day cleanup deadline. Retention on self-hosted servers is decided by their operators.

Deleting your account: in-app Settings → Relay account → Delete account asks the server to clear the online account, files, device records, and credentials. Account deletion does not rewrite existing operational logs or offline copies an operator created separately; for such data, contact the operator through the channels in section 10 — requests are verified before processing. Do not post private files, passwords, or verification codes in public feedback.

If file cleanup fails to complete due to a storage fault, the service retries at startup and in a maintenance pass every 10 minutes. Persistent failures need operator attention; the maintenance log records the count of directories not yet cleaned.

Signing out: immediately clears local login and inbox state and tries to revoke the current device credential; when offline, the server may not have received the revocation. You can remove the device from another signed-in one. Signing out does not delete server files used by other devices.

Clearing the cache: Settings → Local cache → Clear empties downloaded deliveries and snapshots on this device at any time.

Uninstalling: removes preferences and cache inside the app sandbox; the keychain entry on iOS is not guaranteed to be removed with uninstall (system behavior) — sign out in the app before uninstalling.

10. Policy updates & feedback

Updates to this policy are published on this page, with the effective date at the top updated in the same batch.

Feedback channel: GitHub Issues (kk0x03/kodeoff-release). Questions about data handling or deletion requests go through the same channel; state only the request type and a public contact route — never post account credentials or private content.
